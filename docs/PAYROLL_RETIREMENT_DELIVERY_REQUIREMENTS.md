## Configuration and authorization

- Bind an independently reviewed delivery contract to the employer, current plan, recordkeeper identity and allocation-format revision. Preserve immutable revisions, suspension and historical configuration for recovery.
- Initial transport assumption: support SFTP when the actual recordkeeper accepts the reviewed CSV. Do not infer SFTP support from the provider name or assume the existing eight-column format is accepted. Other required provider adapters remain in scope.
- Retain the actual endpoint, authentication, independently verified server identity, submission directory, naming rules, temporary-file handling, receipt location and interpretation. Encrypt credentials and identifiers; never expose them in logs or ordinary history responses.
- Verify whether file ingestion causes a funds debit. A bank credit plus an allocation-triggered debit must not be authorized as two independent harmless steps. The existing separate CCD workflow requires a contract without an additional debit.
- Authorize exact retained allocation bytes, their digest, destination revision and delivery window. Changed configuration or contribution evidence requires renewed authorization before a first send. Suspension stops new sends while retaining read-only recovery of prior attempts.

## Dispatch and recovery

- Commit an immutable delivery claim before the first remote write. Concurrent workers and repeated requests must use the same identity and must not create a second delivery.
- Use a reviewed deterministic filename and bounded connection/operation deadlines. Never overwrite a different file. Partial uploads must remain outside the provider's ingestion path until the reviewed transfer protocol completes.
- A dropped connection after a remote operation leaves an uncertain outcome. Recovery inspects retained remote evidence without automatically repeating delivery. A missing file alone is insufficient proof of non-delivery: the recordkeeper may have consumed it.
- Separate transport verification, file acceptance, trustee receipt and participant posting. Each observation must bind the exact file identity and contribution amounts. Bank evidence remains a separate channel.
- Detect mismatched files, rejected/partial allocations, duplicates, later reversals and unreadable or contradictory receipts. Preserve observations and open actionable internal exceptions rather than closing the batch from a successful upload.
- Scheduling and automatic receipt polling must be bounded, employer-scoped and recoverable across process restarts. Do not hold a database transaction open for an entire remote upload.

## Receipt and employee acceptance

- Implement the actual provider's receipt contract; do not require a fabricated universal receipt format. Retain the provider batch identity, source-file binding, receipt time and each participant's accepted/rejected amounts by contribution category.
- Reconcile all participant rows and integer-cent totals against the authorized file, including missing, duplicate and unexpected rows. Partial acceptance needs a reviewed correction process that cannot resend accepted contributions.
- Employee views show their own deduction and delivery/acceptance status, with support requests for unresolved exceptions. Private provider IDs, credentials and other employees' records stay inaccessible.
- Complete accounting only from the appropriate retained bank and allocation evidence; include returns, corrections and outside contributions in reconciliation.
