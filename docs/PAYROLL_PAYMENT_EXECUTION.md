# Payroll payment execution

Implementation checkpoint, September 10, 2026: admins can configure funding, link verified employee accounts, retain employee consent, authorize a reviewed run and explicitly submit each ACH instruction from the payroll page. Read-only recovery retains provider status without resubmission. Settlement reconciliation, completed-batch finalization, scheduling and complete new-account enrollment remain unfinished. Existing manual finalization records external payment evidence and cannot bypass an active payment batch.

## Provider assumption

Use Modern Treasury with a connected employer bank for USD ACH PPD employee credits. This is an implementation assumption, not an account purchase or a claim that the employer already has this integration. Credentials and read-only funding verification are available in the application. Linking an existing verified employee account and retaining consent are implemented; creating/verifying new accounts internally remains required. Bank account numbers are not stored in the instruction ledger.

The adapter uses the documented [payment-order creation contract](https://docs.moderntreasury.com/platform/reference/create-payment-order), [internal accounts](https://docs.moderntreasury.com/platform/reference/internal-accounts-overview) and [external accounts](https://docs.moderntreasury.com/platform/reference/external-account-object). It requires matching test/live account modes, USD origin currency and a verified recipient account before creating an order. Verification is a transport prerequisite; it does not establish employee authorization or ownership by itself.

## Implemented foundation

- `paymentDispatch.js` is an internal coordinator for retained ACH instructions. It verifies the current authorized plan before claiming, commits a unique claim before provider I/O and appends immutable sanitized observations. Existing claims use read-only provider recovery. It holds the connection lock across I/O and releases settings/run locks after the claim, avoiding reacquisition while other actions may wait. An authenticated, facility/run-scoped admin endpoint supplies transport and calculation dependencies. SUBMIT requires confirmation and the retained fingerprint. RECOVER cannot create a dispatch claim. Concurrent/repeated submission requests become read-only recovery after the first durable claim. No scheduler invokes it yet.

- `paymentBatch.js` and `PaymentBatch.tsx` authorize the reviewed plan, retain an immutable batch and its stable direct-deposit instructions, and allow cancellation before dispatch. Plan inputs are revalidated under locks. The API and database block manual finalization/voiding while a batch remains active. Cancellation and dispatch claims use shared locking and immutable evidence; a claim prevents cancellation unless retained observations prove a definite pre-submission account-check failure and contain no provider payment evidence. Authorization does not call the provider.

- `paymentPlan.js` and `PaymentPlan.tsx` prepare a run-level payment review from an approved, revalidated calculation. They group positive net amounts by reviewed check/direct-deposit elections, identify zero-net lines, apply current bank readiness and reconcile employee net amounts to the run. The plan includes a fingerprint consumed by the authorization and dispatch coordinators. Its transaction is always rolled back, including shared initialization by calculation helpers. It creates no payment instructions and submits no payments.

- `paymentDestination.js` and `PaymentDestination.tsx` link an existing verified provider account from People & onboarding. Read-only lookup checks individual checking/savings details, counterparty, environment and an unambiguous account suffix. Selected provider references and review evidence are encrypted; admin display uses holder/type/last-four/mode. Destinations are immutable and bound to a connection revision. Linking leaves employee authorization required and never activates direct deposit.
- `paymentAuthorization.js` and `EmployeePaymentAuthorization.tsx` add employee review, signature, authorization, withdrawal and downloadable confirmations. The latest account and displayed employer-specific terms are revalidated under session/connection/destination locks. Immutable encrypted receipts preserve signatures and disclosures; withdrawals retain session identity and decision without requiring decryption. Former employees can withdraw but cannot authorize. Payment setup and first dispatch both consume the current record.
- `paymentReadiness.js` now connects retained enrollment evidence to employee pay setup. Direct-deposit pay review requires LIVE mode, the current connection/destination, current signed terms and a latest passed funding check. Missing, changed, withdrawn, test-only or unavailable evidence blocks review with an explicit issue. The pay-review fingerprint includes the retained evidence, preventing a manual ACTIVE flag or stale review from bypassing it. First dispatch consumes the same evidence under its execution locks.

- `paymentConnection.js` and `PaymentConnection.tsx` provide authenticated employer configuration with immutable encrypted revisions, facility isolation, stale-edit protection and metadata-only history. The form clears API keys after save attempts. Saved configuration is explicitly unverified and cannot authorize execution.
- Admins can run a read-only funding-account check for the current configuration. It verifies provider access, account identity, USD currency and matching test/live mode. Immutable outcomes are revision-specific and sanitize errors. The UI shows the latest check and retained history; replacement credentials start without verification. A passed check does not establish funds availability or authorize payment.

- `paymentInstructions.js` retains one immutable instruction per facility, payroll run, employee and mode. Concurrent retention uses a transaction lock and a database unique constraint. Changed destinations, amounts or dates cannot silently replace an instruction. The database verifies approved run ownership, employee net amount, approved payment date and the retained calculation snapshot.
- `modernTreasuryPayments.js` uses integer cents and stable external IDs. It looks up an existing order before creation, bounds requests and recovers a create conflict by lookup. It never automatically repeats a POST within one call. No default network transport is enabled.
- Read-only recovery performs one GET. Missing evidence remains NOT_FOUND; errors or mismatched receipts remain UNCERTAIN. Neither result authorizes another payment.
- Provider receipts distinguish approval, processing, completion, returns, reversals and other exceptions. Changed payment dates and reconciliation state remain explicit. No receipt automatically finalizes payroll.

Modern Treasury's [idempotency keys](https://docs.moderntreasury.com/platform/reference/idempotent-requests) have a 24-hour cache and are scoped to an API key. The adapter also supplies a stable, immutable [external ID](https://docs.moderntreasury.com/platform/reference/external-ids), so durable identity does not depend solely on that cache. The [payment lifecycle](https://docs.moderntreasury.com/platform/reference/payment-order-object) permits an ACH return after completion; completion alone is insufficient to infer final settlement.

## Posted bank evidence

Read-only recovery of a completed, reconciled order now verifies parent bank transactions and matching payment-order line items. The [transaction contract](https://docs.moderntreasury.com/platform/reference/transaction-object) distinguishes posted entries from pending activity. The [line-item contract](https://docs.moderntreasury.com/platform/reference/transaction-line-item-object) supports individual payments inside bulk ACH debits, and [line-item listing](https://docs.moderntreasury.com/platform/reference/list-transaction-line-items) provides parent-transaction filtering and cursor pagination.

The adapter requires the retained originating account/environment, a posted USD debit, valid bank date and matching originating payment-order line-item amounts. It verifies the full sum against the instruction, detects duplicate line items and enforces bounded pagination/deadlines. It re-reads the order after bank verification and rejects changed status/evidence. Sanitized BANK_POSTED evidence is retained in the existing immutable observation ledger; later returned/reversed/failed states show EXCEPTION. The UI displays current bank-evidence status. This is the evidence foundation for closeout; run finalization and post-finalization return handling remain unfinished.

## Retained QuickBooks bank/clearing mapping

`paymentAccountingMapping.js` and the Reports & QuickBooks form bind the payroll funding connection to a reviewed QuickBooks bank/clearing pair. Choices come from the existing chart-of-accounts action. Verification reads the selected Account records and Preferences; it requires an active Bank account, a distinct active Other Current Liability account, USD home currency, no conflicting account currency, exact returned IDs, and agreement with the payroll journal's clearing selection. Only selected metadata is retained, excluding account numbers and access tokens. The bookkeeper attests to the cross-system bank identity.

The immutable mapping includes the payment connection revision, originating provider account, QuickBooks realm/environment, disconnect generation and review reference. Local state becomes CHANGED when those bindings or the payroll-clearing choice change. Provider account state must still be rechecked before posting; CURRENT means the saved local bindings still match. Saving a mapping does not create a journal. Separate settlement-posting controls use the retained mapping.
